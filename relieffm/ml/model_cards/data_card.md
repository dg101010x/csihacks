# Data Card: relief_data (ReliefSim synthetic population)

Fields per AGENTS_FM.md §129.

## Source
100% synthetic. Generated by `ml/simulator/` (ReliefSim v1) — no real
household, transaction, or account data of any kind.

## Permission
N/A — synthetic. No consent/licensing constraints apply.

## Collection period
N/A — generated on demand at training time, not collected.

## Population
Synthetic households with independently sampled parameters (§36): income
amount/frequency/reliability/volatility, fixed/essential/discretionary
spending levels and volatility, reserve level, debt burden, obligation
count, credit utilization, shock frequency/severity/recovery duration.
Explicitly not built from demographic personas or archetypes.

**Actual generated populations:**

- Nano (`runs/nano_20260725_110729/dataset/manifest.json`): 30,000
  households, 3,349,178 events, seed 1.
- Mini (`runs/mini_20260725_122238/dataset/manifest.json`): 25,000
  households, 3,736,473 events, seed 1, generated
  2026-07-25T19:30:28Z.

Both manifests record `git_commit: unknown` because the runs preceded the
repository's first project commit. Their immutable run IDs, manifests,
artifact hashes, and this release commit provide the recoverable lineage.

## Schema
Six token classes (§12): household state, account state, obligation,
historical event, known-future event, and intervention. Intervention
pairs are generated by `ml/simulator/interventions.py`; Nano does not
consume them, while Mini trains against one eligible pair or a masked
placeholder per household. Canonical fields and enums:
`packages/relief_contracts/schemas.py`.

## Preprocessing
`ml/datasets/compile.py` splits each household's simulated future into a
deterministic known component (ledger-replayed from `known_future_events`
only) and an uncertain residual (everything else) — see that module's
docstring for why. `ml/relieffm/tokenize.py` converts to fixed-shape
tensors: amount transform `sign(a)·log(1+|a|)` in dollars (§14), Fourier
day-of-week/day-of-month features + linear time offsets (§15), categorical
embeddings for event/status/direction/recurrence/source/account-role/
merchant-category (§13).

## Missingness
None by construction — every field the simulator emits is fully populated.
This is a real limitation, not a strength: the tokenizer's sparse/stale
data warnings are exercised at inference time against real-shaped
snapshots, never against this training data.

## Split design
Household-level, hash-based (§47, `ml/datasets/splits.py`): sha256(household_id)
mod 100 → train (0-79) / val (80-89) / test (90-99). Deterministic —
the same household_id always lands in the same split, including across
re-generation with the same seed. Actual split for the 30,000-household
Nano run: 24,048 train / 3,007 val / 2,945 test. Actual split for the
25,000-household Mini run: 20,035 train / 2,516 val / 2,449 test.

## Leakage controls
- Future transactions cannot appear in historical features: the tokenizer
  only reads `historical_events` (occurrence_time ≤ as_of) and
  `known_future_events` (Plan-Two-authoritative), never the raw uncertain
  future stream, when building model *inputs*.
- No household appears in more than one split (by construction — split is
  a pure function of household_id).
- No repeated random seeds across splits (each household gets a unique
  per-household seed derived from the population seed + index,
  `ml/simulator/population.py`).
- Model selection was not performed against `run_eval.py`'s held-out
  population in this session (no hyperparameter sweep was run at all).

## Known biases
Unvalidated against any real population (§43's realism checks were run
informally during development — see the two bugs documented below — but
no formal comparison against real aggregate distributions exists, because
no real/public/partner dataset was used this session, per §43's own
requirement not to advance a model on simulator performance alone).

Two generator bugs were found and fixed during this session, worth
disclosing because they shaped every number in this card and the model
card:
1. Checking-account starting balances were drawn from
   `lognormal(mean=7.2)`, giving a median of ~$13 rather than the
   intended ~$1,000 — this alone pushed ~99% of synthetic households into
   apparent 30-day distress. Fixed to `lognormal(mean=11.5, sigma=0.9)`.
2. Rent/mortgage sizing used `income_amount_cents` (a *per-pay-period*
   figure) as if it were monthly income, so weekly/biweekly earners got
   implausibly cheap housing and monthly earners implausibly expensive
   housing. Fixed to normalize to actual monthly income first.
After both fixes, ~48% of synthetic households still show a negative
checking balance within 30 days — plausibly high for a "financial
resilience" population by design, but not validated against anything real,
and should not be read as an estimate of real household distress rates.

## Sensitive fields
None — no PII exists in synthetic data. `merchant_category` uses fixed
category buckets (§16 Level One), no raw merchant text.

## Retention
N/A — regenerated on demand; nothing is retained beyond what a given
training run writes to `runs/<run_id>/dataset/`.

## Deletion process
Delete the GCS run directory (`gs://<bucket>/runs/<run_id>/`) and any
local `runs/` copy. The Git repository stores only release metadata and
hashes, never the Parquet data or checkpoint binaries.

## Intended model uses
Architecture development, pipeline validation, and initial directional
signal on trajectory, distress, event-set, and intervention heads.
Explicitly **not** sufficient on its own to justify production deployment
or advancement (§115) — synthetic success must not be presented as
production validation (§34).

## Prohibited uses
Same as the model card's prohibited-use list — this dataset should not be
cited as evidence for any real-world household behavior claim.
